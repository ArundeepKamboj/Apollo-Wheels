# MVP coverage and build checklist

This is the implementation-status companion to [Apollo_Wheels_MVP_Requirements.md](../Apollo_Wheels_MVP_Requirements.md). It maps the agreed MVP scope to acceptance checks and current code. A feature is not considered complete merely because it appears in a requirement or an architecture diagram.

## Status key

- **Implemented:** available in the local demo and covered by a focused check.
- **Partial:** a basic path exists, but one or more acceptance details are missing.
- **Not implemented:** required scope is documented but the capability is not built yet.
- **Decision/default:** use the documented synthetic/demo behavior until the business rule is confirmed; do not claim it is Wheels policy.

## Remaining MVP build work, in priority order

### P0 — required for an honest MVP demonstration

1. Add source highlight/navigation from a reviewed field to its corresponding PDF page/region. For current synthetic PDFs, marker-level text mapping can be used; do not label it general-purpose legal clause highlighting.
2. Extend end-to-end functional coverage for mismatched client IDs, duplicate/idempotent submissions, and multi-invoice/version edge cases. The standard upload, edit, approval, billing, audit, and history browser path is already covered.
3. Harden the document/API paths for clear errors, malformed/unsupported PDF rows, mismatched client IDs, and duplicate invoice/pricing submissions. Define which failures can be retried safely.
4. Extend demo fixtures/audit tests for unsupported billed charges and one-time setup timing. Existing checks cover missing pricing, missing billing lines, rate/quantity differences, lease/service streams, date filters, and the intentional rate mismatch.
5. Add an explicit combined client billing view/report that preserves service versus lease source labels, or record a specific MVP deferral if the demo only needs separate histories. Do not conflate this with client-facing invoice/email delivery.
6. Prepare a repeatable demo script and deliverable presentation if required for the assessment; document expected outputs and limitations.

### P1 — required before treating extraction/pricing behavior as dependable

1. Define and validate per-service pricing rules for all 13 services; synthetic catalogue presence alone does not prove every calculation works.
2. Add reviewed extraction fixtures with natural language, missing/ambiguous/conflicting clauses, amendment/version cases, and field-level expected outputs. Only then evaluate the optional LLM and report measured results.
3. Define billing period overlap semantics, rates/amount calculations and tolerance, one-time charges, effective-date/version overlap, duplicate invoices, and whether financial impact is in MVP.
4. Add testable audit cases for no billing document at all versus a missing line in a period with an invoice. Current audit can only infer missing charges for periods represented by uploaded invoices.

## Explicitly outside MVP

- Client-facing agreement negotiation, reusable agreement templates, stored negotiation chat, client logins, and auto-generated contract documents.
- OCR for image-only/scanned PDFs and reliable extraction of arbitrary legal prose.
- Client-facing invoice/pricing PDF generation and email/website delivery. The Finance-controlled include-history preference is stored as a future setting only.
- Real Pricing Manager/repository integration, production identity/security, production hosting, per-service database deployment, and Kafka/pub-sub.
- Tax, FX, proration, discount, credit, rounding, minimum, or financial-impact calculations until policy is defined.

## Decisions to keep visible

The synthetic demo uses USD, explicit PDF marker rows, a fixed rate tolerance, and the current single-active-pricing-version behavior. These are implementation defaults, not confirmed client terms. No production LLM/model is selected. A presentation/deployment environment or acceptance threshold has not been supplied. Track these in [ASSUMPTIONS.md](ASSUMPTIONS.md) and resolve only when they block a specific MVP acceptance criterion.
